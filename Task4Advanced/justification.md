# Обоснование выбора событийного подхода

## 1. Текущие проблемы архитектуры (Camel + DWH)

### Проблемы синхронной интеграции через ESB (Apache Camel)

| Проблема                  | Описание                                                          | Влияние на бизнес                                   |
|---------------------------|-------------------------------------------------------------------|-----------------------------------------------------|
| Жёсткая связанность       | При изменении одного сервиса требуется обновлять все интеграции   | Высокое время вывода новых функций (Time-to-Market) |
| Единая точка отказа       | Отказ ESB парализует все интеграции между системами               | Риск остановки критических процессов                |
| Сложность масштабирования | ESB становится узким местом при росте нагрузки                    | Невозможность обрабатывать пиковые нагрузки         |
| Синхронные блокировки     | Сервисы ожидают ответа друг от друга, создавая цепочки блокировок | Деградация производительности                       |
| Сложность отладки         | Трассировка запросов через ESB затруднена                         | Высокое Mean Time To Resolution (MTTR)              |

### Проблемы хранения бизнес-логики в DWH

| Проблема                  | Описание                                               | Влияние на бизнес                       |
|---------------------------|--------------------------------------------------------|-----------------------------------------|
| Низкая производительность | Batch-обработка с задержками в часы                    | Невозможность near-real-time отчётности |
| Жёсткая схема             | Изменение структуры данных требует длительных миграций | Низкая гибкость                         |
| Немасштабируемость        | SQL Server 2008 не справляется с объёмами              | Ограничение роста бизнеса               |
| Смешение логики           | Бизнес-логика в хранимых процедурах и ETL              | Высокая сложность поддержки             |
| Монолитность              | Один DWH для всех задач                                | Конфликт потребностей разных доменов    |

## 2. Преимущества событийного подхода

### Гибкость (Flexibility)

| Аспект                       | Текущее состояние                    | Событийный подход                         |
|------------------------------|--------------------------------------|-------------------------------------------|
| Добавление нового подписчика | Требуется изменение ESB и DWH        | Просто подписать новый сервис на событие  |
| Изменение формата данных     | Каскадное обновление всех интеграций | Версионирование событий                   |
| A/B тестирование             | Сложно                               | Разные подписчики на разные версии        |
| Поэтапный отказ от легаси    | Трудно                               | ACL (Anti-Corruption Layer) как подписчик |

Пример: При добавлении нового страхового партнёра достаточно подписать его сервис на события `PolicyIssued` и
`ClaimFiled`. Никаких изменений в существующих системах не требуется.

### Масштабируемость (Scalability)

| Аспект              | Текущее состояние                | Событийный подход                   |
|---------------------|----------------------------------|-------------------------------------|
| Рост объёма событий | Упирается в ESB                  | Kafka горизонтально масштабируется  |
| Обработка пиков     | Буферизация ограничена           | Kafka хранит события до обработки   |
| Добавление доменов  | Требуется перестройка интеграций | Новый домен публикует/подписывается |
| Load balancing      | Сложно                           | Consumer groups в Kafka             |

Пример: В час пик (утренние записи к врачам) количество событий может вырасти в 10 раз. Kafka легко масштабируется
добавлением брокеров и партиций.

### Скорость реакции (Reactivity)

| Аспект                 | Текущее состояние | Событийный подход       |
|------------------------|-------------------|-------------------------|
| Время реакции          | Часы (batch)      | Секунды (stream)        |
| Обновление аналитики   | Ежедневные отчёты | Near-real-time дашборды |
| Обнаружение аномалий   | Постфактум        | Мгновенные алерты       |
| Клиентские уведомления | Отложенные        | Мгновенные push         |

Пример: При получении критического результата лаборатории (событие `LabResultAvailable`) ИИ-диагностика может
запуститься немедленно, а не ждать ночного batch-процесса.

## 3. Сравнение архитектурных подходов

### Матрица сравнения

| Критерий            | ESB + DWH (текущая)       | Событийная архитектура (целевая) |
|---------------------|---------------------------|----------------------------------|
| Связанность         | Высокая (жесткая)         | Низкая (слабосвязанная)          |
| Производительность  | Batch (часы)              | Stream (секунды)                 |
| Масштабируемость    | Вертикальная (ограничена) | Горизонтальная (без ограничений) |
| Отказоустойчивость  | Низкая (SPOF - ESB)       | Высокая (Kafka cluster)          |
| Time-to-market      | Месяцы                    | Недели                           |
| Сложность поддержки | Высокая                   | Средняя                          |
| Observability       | Низкая                    | Высокая (tracing, метрики)       |
| Откат изменений     | Сложный                   | Простой (версии событий)         |

## 4. Ключевые бизнес-выгоды

### Ускорение Time-to-Market

| Сценарий                           | Текущая оценка | Событийная оценка |
|------------------------------------|----------------|-------------------|
| Добавление нового источника данных | 3-4 недели     | 3-5 дней          |
| Интеграция нового партнёра         | 6-8 недель     | 1-2 недели        |
| Запуск новой фичи в домене         | 4-6 недель     | 1-2 недели        |
| Внедрение новой ИИ-модели          | 2-3 недели     | 3-5 дней          |

### Повышение производительности

| Метрика                       | Текущая        | Целевая        | Улучшение |
|-------------------------------|----------------|----------------|-----------|
| Время формирования отчёта     | Часы           | Секунды        | 1000x     |
| Lag между событием и реакцией | Часы           | Секунды        | 1000x     |
| Пропускная способность        | 1K событий/мин | 1M событий/мин | 1000x     |
| Время восстановления (MTTR)   | Часы           | Минуты         | 60x       |

### Снижение рисков

| Риск                    | ESB + DWH       | Событийная архитектура     |
|-------------------------|-----------------|----------------------------|
| Потеря данных           | Высокий         | Низкий (Kafka persistence) |
| Отказ интеграции        | Критический     | Низкий (децентрализация)   |
| Утерянная бизнес-логика | Высокий (в DWH) | Низкий (в доменах)         |
| Невозможность масштаба  | Высокий         | Низкий (горизонт. масштаб) |

## 5. Пример: сценарий лечения пациента

### Текущий процесс (Camel + DWH)

```
1. Пациент записывается к врачу → запись в DWH (batch)
2. Врач ставит диагноз → обновление DWH (следующий batch)
3. Назначение лечения → обновление DWH
4. Финансовый расчёт → ESB вызывает финтех-сервис (синхронно)
5. Отчёт для руководства → следующий день (batch)

Проблемы:
- Задержки между шагами
- Синхронные блокировки на финансовом расчёте
- Отчётность только на следующий день
  ```

### Целевой процесс (событийный)

```
1. Пациент записывается к врачу → событие AppointmentScheduled
2. ИИ анализирует историю → InferenceRequested (асинхронно)
3. Врач ставит диагноз → DiagnosisAdded
4. Страховая проверяет покрытие → Policy проверяет (асинхронно)
5. Назначение лечения → PrescriptionIssued
6. Финансовый расчёт → InvoiceGenerated (автоматически)
7. PaymentCompleted → обновление аналитики (real-time)
8. Руководство видит дашборд (секунды, не дни)

Преимущества:
- Все шаги асинхронные, без блокировок
- ИИ работает параллельно с врачом
- Финансы и аналитика в реальном времени
- Каждый домен развивается независимо
  ```

## 6. Вывод

Переход на событийную архитектуру даёт компании «Будущее 2.0»:

1. Гибкость — новые домены и партнёры интегрируются за недели, а не месяцы
2. Масштабируемость — горизонтальное масштабирование под любой объём данных
3. Скорость — near-real-time аналитика и реакция на события
4. Надёжность — отказ одного домена не парализует всю систему
5. Прозрачность — полная трассировка и observability

Это позволяет бизнесу быстрее реагировать на изменения рынка, запускать новые продукты и масштабироваться на новые
регионы без архитектурных ограничений.
